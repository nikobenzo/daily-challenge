# Android app

A native Android app in `android/`: Kotlin, Jetpack Compose and Material 3, built with Gradle
from the command line. It is the same tracker as the iPhone app (sign in, create account with an
emailed code, password reset, setup with a time zone, Today, History with Edit this day, Account
with sync, water reminders, appearance, sign out and account deletion) and syncs with the Mac and
iPhone apps through the same Supabase project and wire format. There are no widgets yet, and no
Google Play listing, store assets, release signing or upload; those are later phases.

- Package (applicationId): `app.dailychallenge.android`. It cannot change after the first Play
  upload, so confirm it before that.
- minSdk 29 (Android 10, the Redmi Note 7), targetSdk and compileSdk 36.
- Version: `versionName` and `versionCode` in `android/app/build.gradle.kts`. Raise
  `versionCode` for every Play upload.

## Layout

| Path | What it is |
|---|---|
| `android/core/` | Pure Kotlin/JVM library, no Android dependency: the challenge rules (`Challenge.kt`), event wire format (`Wire.kt`), local store and pending queue (`ChallengeStore.kt`), sync coordinator (`Tracker.kt`), auth flow (`AuthModel.kt`), Supabase REST client (`Supabase.kt`), water reminder planning (`WaterReminders.kt`) and the celebration ledger. Ports of `ChallengeCore` and `ChallengeSyncKit`, with the same words. |
| `android/app/` | The Android app: Compose screens in `ui/`, `AppGraph.kt` (composition root), `Platform.kt` (Keystore session store, alarms, notification receiver, WorkManager sync), `MainActivity.kt`. |
| `android/app/src/debug/` | Debug-only offline fixtures (`Fixtures.kt`); release builds use the stub in `src/release/`, so fixtures never ship. |
| `test-vectors/challenge-rules.json` | Shared parity vectors, generated by `test-vectors/generate.py`. The Swift test `Tests/ChallengeCoreTests/ParityVectorTests.swift` and the Kotlin test `ParityVectorTest.kt` both check them, so the two ports cannot drift apart silently. |

## Toolchain (once per Mac)

No sudo and no system symlinks are needed.

```sh
brew install openjdk@21 android-commandlinetools
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home
export ANDROID_HOME=/opt/homebrew/share/android-commandlinetools
sdkmanager "platform-tools" "platforms;android-36" "build-tools;36.0.0"
yes | sdkmanager --licenses
echo "sdk.dir=$ANDROID_HOME" > android/local.properties   # gitignored
```

For an emulator, also `sdkmanager "emulator" "system-images;android-29;google_apis;arm64-v8a"` and
`avdmanager create avd -n dc-api29 -k "system-images;android-29;google_apis;arm64-v8a"`.

The Gradle wrapper (`android/gradlew`, Gradle 8.14.3) is committed and downloads Gradle itself.

## Configuration

The app reads `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` from `.env.local` at the repository
root when it is built, the same file the Mac and iPhone builds use (see `.env.example`). They are
compiled into `BuildConfig`; nothing is committed. The publishable key is public by design;
row-level security protects the data. Never put a secret or service-role key in `.env.local`.

- A Debug build without `.env.local` still builds and opens on "Configuration unavailable".
- A Release build refuses to build without both values.

## Build

```sh
cd android
./gradlew assembleDebug        # app/build/outputs/apk/debug/app-debug.apk
./gradlew :core:test           # rules parity, wire format, store and queue, sync, auth, reminders
./gradlew connectedDebugAndroidTest   # Compose UI tests on a connected phone or emulator
```

`./gradlew assembleRelease` builds a minified release APK but it is unsigned: release signing is a
later owner step (Play App Signing with an upload key the owner creates and keeps; never commit a
keystore, `*.jks` and `*.keystore` are gitignored).

## Install on a phone

1. On the phone: Settings > About phone, tap MIUI version (or Build number) seven times; then
   Settings > Additional settings > Developer options: turn on **USB debugging**, and on MIUI also
   **Install via USB** and **USB debugging (Security settings)**. MIUI asks you to sign in to a
   Mi account to turn these on.
2. Connect by USB, accept the "Allow USB debugging" prompt, and check `adb devices` lists it.
3. `adb install -r android/app/build/outputs/apk/debug/app-debug.apk`, then open Daily Challenge.
   MIUI may show its own install confirmation on the phone; accept it.

A Debug build signs with the local debug key, so installing a Play build later needs the Debug
build uninstalled first (Settings > Apps > Daily Challenge > Uninstall). That deletes this phone's
local copy, so sync first.

## Debug fixtures and screenshots

Debug builds accept a fixture on launch. A fixture opens offline sample data in a temporary
folder with a fixed clock (Friday 9 October 2026, 15:00 in Jersey): it never reads the real
session, never networks, and never sets an alarm or posts a notification.

```sh
adb shell am start -S -n app.dailychallenge.android/.MainActivity --es fixture today --es appearance dark
```

Screens: `signIn`, `createAccount`, `forgotPassword`, `confirmCode`, `resetPassword`, `checking`,
`setup`, `today`, `todayComplete`, `history`, `account`, `todayExtras`, `extrasCap`,
`historyExtras`, `historyExtrasEditing`, `accountExtras`, `historyCarryOver`. Options:
`--es appearance light|dark|system`, `--ez manageExtras true`, `--ez deleteAccount true`,
`--ez deleteAccountConfirm true`, `--ez deletionFails true`. Capture with
`adb exec-out screencap -p > docs/screenshots/android/<name>.png`. Launching without a fixture
opens the real app again.

Screenshots: `docs/screenshots/android/`. Those in `emulator/` come from an Android 10 (API 29)
emulator at 1080 by 2280, close to the Redmi Note 7's screen; captures from a real phone go
directly in `docs/screenshots/android/`.

## How it matches the other apps

- **Rules and wording:** the five requirements, day status, streaks, milestones, extras with
  carry-over and the "Late" caption, the 10-extra cap, title rules, password rules, error words,
  sync states and activity labels are ported from Swift and use the same words, with "phone"
  for the device and "Android" and "Do Not Disturb" where the iPhone says iOS and Focus.
- **Wire format:** events and the challenge record are encoded exactly as the Swift apps encode
  them (key order, integral numbers, `\/` escapes, uppercase UUIDs, seconds since 2001), so
  rows written by any client decode on every other; the shared vectors cover this.
- **Local data:** one JSON snapshot and pending queue per account in the app's private files,
  written atomically, never reset when unreadable. Sync uploads the queue idempotently, then
  merges the server's events; the server is never asked to change.
- **Session:** Supabase Auth tokens are encrypted with an Android Keystore key (AES-GCM) in
  no-backup app storage; passwords are never stored and nothing is logged. Android backup and
  device-to-device transfer are turned off for the app's data.
- **Sync timing:** on launch, when the app comes to the foreground, every 30 seconds while it is
  on screen, after each change, when the network comes back, and every 30 minutes in the
  background through WorkManager while signed in.
- **Water reminders:** exact-time notifications through `AlarmManager` (no exact-alarm
  permission needed), at most 48 queued, re-planned whenever the total changes, after a reboot,
  an app update or a time zone change, and from the background sync. Android 13 and later ask
  for notification permission when reminders are turned on.
- **Not ported:** widgets (later phase), Mac-only features (backups, launch at login, updates).

## Owner acceptance checklist (real account, real phone)

Workers verified signed-out screens, setup and tracker flows on fixtures only, with the 13 UI
tests on an Android 10 emulator; no real account, sign-in, sync or deletion was used. Use a disposable account for these, never the family's
real history, and confirm the hosted migrations are deployed first (`20261010000100_extras_action_kinds`
for extras, `20261011000100_account_deletion` for deletion; see
[production sync](production-sync.md)).

1. Build with the real `.env.local`, install, open: the sign-in screen appears (not
   "Configuration unavailable").
2. **Create account** with a new address: the code email arrives; **Enter the code** confirms
   and signs in. Resend counts down from 60 s.
3. Sign out on this phone, then **Forgot password?**: the code arrives; a new password with the
   code signs you in.
4. With no challenge on the account, setup appears after "Checking for your existing
   challenge"; start one with the phone's time zone.
5. On the Mac or iPhone, sign in to the same account: the challenge appears there. Pour water
   and tick habits on each device; each change reaches the other within a minute or on Sync now.
6. Turn on airplane mode, make changes: Account says "Saved on this phone, N changes waiting";
   turn it off: they upload and the state returns to "Up to date".
7. History: select a past day, **Edit this day**, correct it; streaks recalculate on every device.
8. Extras: add, tick, rename and archive; check carry-over and "Late" on the next day, and that
   the other devices show the same.
9. Water reminders: turn on, allow notifications, set a short interval; a "Water check-in"
   notification arrives on time with the app closed, and stops once 4,000 ml is reached. On MIUI,
   also check Settings > Apps > Daily Challenge > Battery saver set to "No restrictions" and
   Autostart allowed, since MIUI can hold back alarms for restricted apps; reboot and confirm
   reminders continue.
10. Appearance System / Light / Dark follows and overrides the phone's dark mode.
11. **Delete account** on the disposable account: both confirmations, then the sign-in screen
    says the account was deleted; signing in again fails, and the Mac/iPhone are signed out.
    Offline, deletion fails and changes nothing.

## Remaining owner steps before Google Play (later phases)

- Confirm the package name `app.dailychallenge.android` (permanent after the first upload).
- Create the app in Play Console, enrol in Play App Signing and create an upload key (kept by
  the owner, never committed); add a signing config that reads it from outside the repository.
- Store listing, screenshots, privacy policy URL, Data safety form (email, challenge activity;
  account deletion in app and by request), content rating, and target audience.
- Internal testing track first, on real phones, using the checklist above.
- Widgets for Android (home screen water, requirements and extras), as on the iPhone.
