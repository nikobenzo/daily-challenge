# Android app

A native Android app in `android/`: Kotlin, Jetpack Compose and Material 3, built with Gradle
from the command line. It is the same tracker as the iPhone app (sign in, create account with an
emailed code, password reset, setup with a time zone, Today, History with Edit this day, Account
with sync, water reminders, appearance, sign out and account deletion) and syncs with the Mac and
iPhone apps through the same Supabase project and wire format, with three home-screen widgets
(see [Widgets](#widgets)). Release signing, the Play listing drafts and store graphics are ready;
uploading is the owner's [Google Play release checklist](play-release.md).

- Package (applicationId): `app.dailychallenge.android`. It cannot change after the first Play
  upload, so confirm it before that.
- minSdk 29 (Android 10, the Redmi Note 7), targetSdk and compileSdk 36.
- Version: `versionName` and `versionCode` in `android/app/build.gradle.kts`. `versionCode`
  counts Play uploads: raise it by one for every bundle uploaded to any track
  ([scheme](play-release.md#3-build-the-release-bundle)).

## Layout

| Path | What it is |
|---|---|
| `android/core/` | Pure Kotlin/JVM library, no Android dependency: the challenge rules (`Challenge.kt`), event wire format (`Wire.kt`), local store and pending queue (`ChallengeStore.kt`), sync coordinator (`Tracker.kt`), auth flow (`AuthModel.kt`), Supabase REST client (`Supabase.kt`), water reminder planning (`WaterReminders.kt`) and the celebration ledger. Ports of `ChallengeCore` and `ChallengeSyncKit`, with the same words. |
| `android/app/` | The Android app: Compose screens in `ui/`, `AppGraph.kt` (composition root), `Platform.kt` (Keystore session store, alarms, notification receiver, WorkManager sync), `MainActivity.kt`. |
| `android/app/src/debug/` | Debug-only offline fixtures (`Fixtures.kt`); release builds use the stub in `src/release/`, so fixtures never ship. |
| `test-vectors/challenge-rules.json` | Shared parity vectors, generated by `test-vectors/generate.py`. The Swift test `Tests/ChallengeCoreTests/ParityVectorTests.swift` and the Kotlin test `ParityVectorTest.kt` both check them, so the two ports cannot drift apart silently. |

## Toolchain (once per Mac)

No sudo and no system symlinks are needed.

```sh
brew install openjdk@21 android-commandlinetools
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home
export ANDROID_HOME=/opt/homebrew/share/android-commandlinetools
sdkmanager "platform-tools" "platforms;android-36" "build-tools;36.0.0"
yes | sdkmanager --licenses
echo "sdk.dir=$ANDROID_HOME" > android/local.properties   # gitignored
```

For an emulator, also `sdkmanager "emulator" "system-images;android-29;google_apis;arm64-v8a"` and
`avdmanager create avd -n dc-api29 -k "system-images;android-29;google_apis;arm64-v8a"`.

The Gradle wrapper (`android/gradlew`, Gradle 8.14.3) is committed and downloads Gradle itself.

## Configuration

The app reads `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` from `.env.local` at the repository
root when it is built, the same file the Mac and iPhone builds use (see `.env.example`). They are
compiled into `BuildConfig`; nothing is committed. The publishable key is public by design;
row-level security protects the data. Never put a secret or service-role key in `.env.local`.

- A Debug build without usable values (missing, or still the `.env.example` placeholder
  `your-project`) still builds, prints a Gradle warning, and opens on "Configuration unavailable".
- A Release build refuses to build without both values.

## Build

```sh
cd android
./gradlew assembleDebug        # app/build/outputs/apk/debug/app-debug.apk
./gradlew :core:test           # rules parity, wire format, store and queue, sync, auth, reminders
./gradlew connectedDebugAndroidTest   # Compose UI tests on a connected phone or emulator
```

Release builds (`./gradlew bundleRelease` for Play, `assembleRelease` for a sideloadable APK) are
minified and shrunk with R8 and signed with the owner's Play upload key. The key lives outside the
repository: `scripts/android-upload-key.sh` creates it, and Gradle reads `DC_UPLOAD_STORE_FILE`,
`DC_UPLOAD_STORE_PASSWORD` and `DC_UPLOAD_KEY_ALIAS` from `~/.gradle/gradle.properties` or the
environment, refusing a release build without them or with a keystore inside the repository
([checklist](play-release.md#2-create-the-upload-key-once)). Never commit a keystore; `*.jks` and
`*.keystore` are gitignored.

The release manifest asks for `INTERNET`, `ACCESS_NETWORK_STATE` (sync), `POST_NOTIFICATIONS`
(water reminders, Android 13 and later, asked only when reminders are turned on),
`RECEIVE_BOOT_COMPLETED` (re-plan reminders and background sync after a restart) and `WAKE_LOCK`
(WorkManager), plus AndroidX's signature-only `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`. There is
no exact-alarm permission (reminders use inexact `setAndAllowWhileIdle`), no advertising ID and no
foreground service: WorkManager's `FOREGROUND_SERVICE` and `SystemForegroundService` are removed in
the manifest. Cleartext traffic and backup are off.

## Install on a phone

1. On the phone: Settings > About phone, tap MIUI version (or Build number) seven times; then
   Settings > Additional settings > Developer options: turn on **USB debugging**, and on MIUI also
   **Install via USB** and **USB debugging (Security settings)**. MIUI asks you to sign in to a
   Mi account to turn these on.
2. Connect by USB, accept the "Allow USB debugging" prompt, and check `adb devices` lists it.
3. `adb install -r android/app/build/outputs/apk/debug/app-debug.apk`, then open Daily Challenge.
   MIUI may show its own install confirmation on the phone; accept it.

**MIUI without a SIM card.** MIUI will only turn on **Install via USB** and **USB debugging
(Security settings)** with a SIM in the phone. Without them, `adb install` fails at once with
`INSTALL_FAILED_USER_RESTRICTED` (logcat shows MIUI's `AdbInstallActivity` cancelling it), and
MIUI also blocks `adb shell input` taps and scrcpy control. `adb push`, `adb shell am start`,
`adb exec-out screencap` and `adb logcat` still work, so install by hand:

1. `adb push android/app/build/outputs/apk/debug/app-debug.apk /sdcard/Download/DailyChallenge-debug.apk`
2. On the phone, open Files (File Manager) > Download and tap `DailyChallenge-debug.apk`.
3. The first time, MIUI asks to allow File Manager to install unknown apps; allow it, go back,
   then tap **Install**.

Updating works the same way: push the new APK and install it over the old one, which keeps
the app's data. Debug fixtures and screenshots then need no taps (see below).

A Debug build signs with the local debug key, so installing a Play build later needs the Debug
build uninstalled first (Settings > Apps > Daily Challenge > Uninstall). That deletes this phone's
local copy, so sync first.

## Debug fixtures and screenshots

Debug builds accept a fixture on launch. A fixture opens offline sample data in a temporary
folder with a fixed clock (Friday 9 October 2026, 15:00 in Jersey): it never reads the real
session, never networks, and never sets an alarm or posts a notification.

```sh
adb shell am start -S -n app.dailychallenge.android/.MainActivity --es fixture today --es appearance dark
```

Screens: `signIn`, `createAccount`, `forgotPassword`, `confirmCode`, `resetPassword`, `checking`,
`setup`, `today`, `todayComplete`, `history`, `account`, `todayExtras`, `extrasCap`,
`historyExtras`, `historyExtrasEditing`, `accountExtras`, `historyCarryOver`. Options:
`--es appearance light|dark|system`, `--ez manageExtras true`, `--ez deleteAccount true`,
`--ez deleteAccountConfirm true`, `--ez deletionFails true`. Capture with
`adb exec-out screencap -p > docs/screenshots/android/<name>.png`. Launching without a fixture
opens the real app again.

Screenshots: `docs/screenshots/android/` holds captures from the Redmi Note 7 (Android 10,
MIUI 12.5, 1080 by 2340) taken with these fixture launches, plus `launch-signed-out.png`, the

## How it matches the other apps

- **Rules and wording:** the five requirements, day status, streaks, milestones, extras with
  carry-over and the "Late" caption, the 10-extra cap, title rules, password rules, error words,
  sync states and activity labels are ported from Swift and use the same words, with "phone"
  for the device and "Android" and "Do Not Disturb" where the iPhone says iOS and Focus.
- **Wire format:** events and the challenge record are encoded exactly as the Swift apps encode
  them (key order, integral numbers, `\/` escapes, uppercase UUIDs, seconds since 2001), so
  rows written by any client decode on every other; the shared vectors cover this.
- **Local data:** one JSON snapshot and pending queue per account in the app's private files,
  written atomically, never reset when unreadable. Sync uploads the queue idempotently, then
  merges the server's events; the server is never asked to change.
- **Session:** Supabase Auth tokens are encrypted with an Android Keystore key (AES-GCM) in
  no-backup app storage; passwords are never stored and nothing is logged. Android backup and
  device-to-device transfer are turned off for the app's data.
- **Sync timing:** on launch, when the app comes to the foreground, every 30 seconds while it is
  on screen, after each change, when the network comes back, and every 30 minutes in the
  background through WorkManager while signed in.
- **Water reminders:** exact-time notifications through `AlarmManager` (no exact-alarm
  permission needed), at most 48 queued, re-planned whenever the total changes, after a reboot,
  an app update or a time zone change, and from the background sync. Android 13 and later ask
  for notification permission when reminders are turned on.
- **Not ported:** the iPhone's Lock Screen water ring (Android phones have no equivalent), and
  Mac-only features (backups, launch at login, updates).

## Widgets

Three resizable home-screen widgets, the iPhone set drawn in the Android app's design system
(Jetpack Glance, `android/app/src/main/java/app/dailychallenge/android/widget/`):

- **Water** (2 by 2, wider sizes put the jug beside the total): the Today jug and today's total
  out of 4,000 ml. **+ 450 ml** records a 450 ml pour, also past the goal. **−** undoes today's
  latest pour, whatever its amount or the device it came from; with no pour today it is drawn
  disabled and a stale tap records nothing.
- **Daily requirements** (4 by 2): the day badge, the streak and Today's ring gauges for workout,
  walk, clean diet and Bible reading. Tapping workout, walk or Bible ticks or unticks it. Diet
  flips between pending and clean; a diet marked missed in the app shows a dashed red ring, and
  tapping it opens the app instead of changing it.
- **Extras** (4 by 2, taller sizes show more rows, up to all ten): today's checklist with Late
  markers; tap a row to tick it. When rows do not fit, "Open all N extras" opens Manage extras;
  with none, "Add your own to-dos" does.

Each widget shows the challenge's own date ("12 Oct · Jersey"), so a phone in another time zone
still makes sense. Anything that is not a control opens the app on Today (Extras: Manage extras),
behind sign-in and setup as usual. Signed out, the widgets say "Open Daily Challenge to sign in";
with no challenge yet, "Open Daily Challenge to set up"; with history the app cannot read, "Open
Daily Challenge". They never show another account's data.

**How a tap is recorded.** A tap runs in the app's own process without opening the app, the
session or the network. Inside the store lock it reads the published widget account and today's
stored state at the tap's own time in the challenge's zone, decides the action from that (never
from what the widget last drew), and records one of the existing actions (`pour(450)`,
`undoLatestPour`, `setHabit`, `setDiet`, `setExtra`) into the normal history and pending queue,
exactly as an in-app edit would. The app's own edits, setup and sync merge load the store fresh
inside the same lock (`StoreLock`, a JVM lock plus an advisory file lock), so a widget tap and an
in-app edit or an in-flight sync can never lose or duplicate each other. After a recorded tap the
open app reloads, and one run of the app's sync worker is queued for when there is a network; the
app's sync then uploads the pending events like any others. The widgets never hold a session
token and never make a network request.

**Account binding.** The app publishes `widget-account.json` beside the history: the signed-in
owner and an opaque generation, never a token or an email. Every drawn control carries that
generation and the challenge ID. Sign-out, account deletion and switching account unpublish it
or issue a new generation first, so a tap drawn before is refused (the widget then redraws in its
current state). Archived extras, extras no longer shown today and days outside the challenge are
refused too.

**When they redraw.** After every committed change in the app (edits, setup, sync merges), after a
widget tap, after sign-in or sign-out, and at the next midnight in the challenge's zone through one
inexact alarm that does not wake the phone (it fires at the next wake), re-armed on each redraw
and after a restart or an app update, and cleared when no widget is placed. There is no periodic
update and no background job. On Android 12 and later the widgets follow Light and Dark by
themselves, even with the app closed. On Android 10 and 11 they draw the colours of the moment:
the app redraws them when the theme or font size changes while it is running, and otherwise they
switch at their next redraw (a tap, opening the app, a sync or midnight).

**Accessibility.** Every control has a spoken label with its state ("Workout, 45 min, home or gym,
done", "Undo latest pour, no pour today", "Stretch, late, pending"); the water total is spoken as
"Water, 1,350 of 4,000 millilitres". Text follows the system font size; at large sizes the pour
label shortens, extra titles truncate (and are still spoken in full) and fewer extras rows are
shown, with the "Open all" link kept.

**Limits.** A pour from a widget that reaches 4,000 ml stops water reminders when the app next runs
(the reload after a tap does it when the app is in memory). Undo after midnight acts on the new day.

### Widget fixtures (Debug builds)

```sh
adb shell am start -n app.dailychallenge.android/.MainActivity --es widgetFixture partial
adb shell am start -n app.dailychallenge.android/.MainActivity --es widgetFixture partial --es pinWidget water
adb shell am start -n app.dailychallenge.android/.MainActivity --es widgetFixture off
```

A widget fixture writes synthetic history (day 12 in Jersey, relative to today) into the app's
`WidgetFixtures` folder, points the widgets at it and redraws them; taps then record there.
`off` points them back at the real history. Fixtures: `partial`, `empty`, `complete`, `over`,
`missedDiet`, `extrasMany`, `signedOut`, `noChallenge`, `off`. `--es pinWidget
water|requirements|extras` asks the launcher to place one (it shows "Add to home screen"). The
real session and history are never read or changed. Release builds contain none of this.

Screenshots: `docs/screenshots/android/widgets/`, placed on the home screen of an Android 10
(API 29) emulator in Light and Dark (`<fixture>-water-extras-<theme>.png` and
`<fixture>-requirements-<theme>.png`, plus `partial-*-dark-largetext.png` at the largest font
size), and on an Android 16 (API 36) emulator (`android16-*`; the dark one was taken with the
app's process stopped). Redmi Note 7 captures are `redmi-*`.

### Tests

`WidgetActionsTest` (`./gradlew :core:test`) runs the widget actions against the real store and
lock: pour (also past the goal), undo with and without a pour and of a synced pour, habit ticks
read from storage, diet pending and clean with a missed day left alone, extras ticks and refusals,
refusal after sign-out, account switch and deletion, a binding for another challenge, the day at
the tap time in a New York challenge, an app edit after a widget tap, a tap during an in-flight
sync, and threads racing app edits. `WidgetLayoutTest` (`./gradlew connectedDebugAndroidTest`)
checks the Glance layouts: what each widget shows and speaks, which tap or app link each control
carries, extras rows at small, tall and large-text sizes, and the signed-out state.

## Owner acceptance checklist (real account, real phone)

Workers verified signed-out screens, setup and tracker flows on fixtures only, with the 13 UI
tests on an Android 10 emulator; no real account, sign-in, sync or deletion was used. Use a disposable account for these, never the family's
real history, and confirm the hosted migrations are deployed first (`20261010000100_extras_action_kinds`
for extras, `20261011000100_account_deletion` for deletion; see
[production sync](production-sync.md)).

1. Build with the real `.env.local`, install, open: the sign-in screen appears (not
   "Configuration unavailable").
2. **Create account** with a new address: the code email arrives; **Enter the code** confirms
   and signs in. Resend counts down from 60 s.
3. Sign out on this phone, then **Forgot password?**: the code arrives; a new password with the
   code signs you in.
4. With no challenge on the account, setup appears after "Checking for your existing
   challenge"; start one with the phone's time zone.
5. On the Mac or iPhone, sign in to the same account: the challenge appears there. Pour water
   and tick habits on each device; each change reaches the other within a minute or on Sync now.
6. Turn on airplane mode, make changes: Account says "Saved on this phone, N changes waiting";
   turn it off: they upload and the state returns to "Up to date".
7. History: select a past day, **Edit this day**, correct it; streaks recalculate on every device.
8. Extras: add, tick, rename and archive; check carry-over and "Late" on the next day, and that
   the other devices show the same.
9. Water reminders: turn on, allow notifications, set a short interval; a "Water check-in"
   notification arrives on time with the app closed, and stops once 4,000 ml is reached. On MIUI,
   also check Settings > Apps > Daily Challenge > Battery saver set to "No restrictions" and
   Autostart allowed, since MIUI can hold back alarms for restricted apps; reboot and confirm
   reminders continue.
10. Appearance System / Light / Dark follows and overrides the phone's dark mode.
11. **Delete account** on the disposable account: both confirmations, then the sign-in screen
    says the account was deleted; signing in again fails, and the Mac/iPhone are signed out.
    Offline, deletion fails and changes nothing.

### Widgets (real account, real phones)

Use the same disposable account, signed in on this phone, the Mac and the iPhone.

1. Long-press the home screen, Widgets, Daily Challenge: add Water, Daily requirements and
   Extras. Each shows today's data and the challenge date.
2. With the app closed, tap **+ 450 ml** twice and **−** once, tick workout, flip diet to clean
   and tick an extra. Each widget updates at once.
3. Open the app: Today shows the same. Within a minute (or on Sync now), the Mac and the iPhone
   show the pour, the undo and the ticks; nothing is doubled.
4. Turn on airplane mode, tap a few widget controls, open the app: Account says the changes are
   waiting; turn airplane mode off and they upload.
5. On the Mac or iPhone, add a pour and archive an extra; after the phone's next sync (open the
   app, or wait for background sync) the widgets show both, and the archived extra cannot be
   ticked.
6. Mark diet missed in the app: the widget shows a dashed red ring, and tapping it opens the app.
7. Sign out in the app: all three widgets say "Open Daily Challenge to sign in", and no tap
   records anything. Sign in again and they return.
8. Leave the widgets placed past midnight in the challenge's zone: the next morning they show
   the new day (0 ml, pending rings, carried-over extras marked Late).
9. Switch the phone between Light and Dark: the widgets follow (on Android 10, at once if the app
   is running, otherwise at their next update).
10. TalkBack: each ring, button and extra is read with its state.
11. On MIUI, set Settings > Apps > Manage apps > Daily Challenge > Battery saver to "No
    restrictions" and allow Autostart. MIUI can otherwise stop the app in the background, which
    delays the midnight redraw (until the next unlock, tap or app launch) and the sync after a
    widget tap (until the app is opened). Taps themselves still record.
