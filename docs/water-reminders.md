# Water reminders

Account settings, next to Appearance, contain an opt-in **Water reminders on this
Mac** toggle, interval, and active window in the challenge's timezone. Default: off,
every 90 minutes, 09:00–21:00 in that timezone (Europe/Jersey for challenges
started before timezones were chosen). Defaults yield 09:00, 10:30, 12:00, 13:30, 15:00,
16:30, 18:00, 19:30, 21:00. The end is inclusive only when it is an anchored slot.
Intervals are configurable from 15 to 240 minutes (UI steps of 15); the window
is same-day, with minute precision. Invalid/reversed windows are not saved.

Preferences persist in this Mac's UserDefaults, not challenge records or sync.
Enable only the chosen reminding Mac; enabling one never enables another. Native
permission is requested only on off→on. Settings show the actual permission
state (not determined, denied, allowed, or checking), permission/scheduling errors,
and **System Settings > Notifications > Daily Challenge** guidance. Turning on a
toggle is not evidence that macOS authorized notification delivery.

## Scheduling and limits

- Pure `ChallengeCore/WaterReminders.swift` injects a clock and computes strictly
  future calendar slots in the challenge's timezone through the scheduling
  horizon, independently of device timezone. Eligibility uses each slot's day's locally known water total.
  A configured midnight slot can therefore be queued in the preceding minute,
  even when the preceding day is complete. DST missing times are skipped;
  repeated wall times are used once, first occurrence.
- `WaterReminderController` uses a fakeable centre and a thin native adapter. It
  schedules **at most one request within the next minute**, checking every 15
  seconds independently of popup visibility. Requests use absolute date
  components in the challenge's timezone, never repeating intervals. The app must be
  running and awake; this is not a background service or launch-at-login feature.
- Local edits, incoming synced activity, account changes, periodic day rollover,
  settings/permission changes and wake reconcile the pending request. Sleep and
  normal quit cancel it. Relaunch/wake discard obsolete slots, never replay them
  or submit an accumulated batch. Late asynchronous adds are cancelled after
  newer state wins; already presented notifications cannot be recalled reliably.
- At 4,000 ml or more on the **target day**, cancel that day's reminder; an
  undo/correction below target resumes future slots only. A selected historical
  day does not affect reminder eligibility.
  No active local challenge/account means no requests. There are no notifications
  for any non-water requirement.
- macOS ultimately controls presentation. Focus, permissions, system delays, a
  process crash, or sleep racing delivery can prevent or defer an already accepted
  request. We request only in-window times, but cannot guarantee the OS presents
  at that exact time or suppresses an already deferred banner. No catch-up batch
  is generated by the app. A short horizon and sleep cancellation minimize stale
  pending work; they are not an OS delivery guarantee.
- If the other Mac is offline or hasn't synced, locally unknown completion
  cannot cancel a reminder. Both Macs enabled can duplicate reminders; there is
  no exactly-once cross-Mac claim. Wording asks to check the log and drink only
  what remains toward the target, never beyond it.

## Verification

`swift test` covers the pure planner (default slots, inclusive 21:00 boundary,
custom windows/intervals, goal/undo, midnight, both Jersey DST transitions,
New York and Sydney windows including Sydney's skipped hour,
missing/repeated local times) and fake-centre reconciliation (grant/denial,
authorization/add failures, preferences, completion/undo, sign-out, stale async
add, sleep/wake, day rollover, history selection and actual incoming sync).
These tests use temporary accounts/directories and independent defaults suites;
none calls UserNotifications or production Keychain. On 8 October 2026, the full
`swift test` suite passed: 78 tests (including 15 new planner/reconciliation tests).
`git diff --check` also passed. No cloud CI is configured.

The separate explicit OS probe is `bash scripts/test-notification-fixture.sh`.
It may request native permission and, if granted, post one clearly labelled
FIXTURE notification. It is not part of automated tests. Both the initial probe
and registered GUI-launch probe were refused on macOS 27.0.1. **Native delivery
was not verified**; see [exact evidence](notification-fixture-verification.md).
No signing, security, notification, or Focus settings were changed.

Required PR limitation: native fixture authorization was refused; actual native
notification delivery remains unverified. Automated midnight regressions use a
fake notification centre and do not change that acceptance limitation.

## Owner acceptance

The owner, not automated testing, installs the updated real app without running
two writers. Keep the same app login and identifiers; never reset challenge data.

- [ ] Choose one Mac to remind; leave the other off. Enable in Account and allow
  the native permission request if offered. If refused/denied, inspect System
  Settings > Notifications > Daily Challenge. Record real authorization state;
  do not bypass device policy or signing controls.
- [ ] Keep the app running and awake through a future eligible slot;
  confirm real delivery with permission allowed. Record Focus/system limitations
  separately; fake-centre success does not prove this check.
- [ ] Change interval/window and verify only new future slots, including 21:00
  when eligible. No workout/walk/diet/reading notifications.
- [ ] Reach 4,000 ml and confirm cancellation. Undo below target and confirm only
  the next eligible future reminder (no immediate accumulated reminders).
- [ ] Complete on the other Mac, sync to the reminding Mac, and confirm
  cancellation. Repeat while offline to understand why cancellation must wait.
- [ ] Sleep across slots, wake, and relaunch after missed slots: no burst. Check
  outside-window behavior, the challenge's next day, and DST when applicable; automated
  tests cover transitions without changing the Mac's clock or timezone.
- [ ] Relaunch preserves this Mac's settings, without enabling the other Mac.
  Denying/revoking permission is reported truthfully rather than as active delivery.
